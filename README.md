# Compact WholeBody ONNX — GitHub Actions parallel training

複数映像を処理する際の推論コストを優先したWholeBody姿勢推定パイプラインです。COCO-WholeBodyの教師から用途に必要な関節を選び、軽い共有特徴から位置を推定します。複数のGitHub Actionsジョブが同じモデルの勾配を計算し、COCOの実画像・2DラベルとASPset-510の実測3D関節で共通の学習状態を更新して、学習済みONNXをHugging Faceへ公開する構成です。

開発元は [DaisukeDaisuke/Wholebody-onnx](https://github.com/DaisukeDaisuke/Wholebody-onnx) です。以下のHugging Faceリポジトリは、このパイプラインのGitHub Actionsから新規作成する配布先です。URLの記載だけを、学習・公開完了の報告とは扱いません。

| 用途 | 配布先 |
|---|---|
| 公開モデル・ONNX・モデル情報 | [RabbitDaisuke/Wholebody-Compact-20261102-a6fde3](https://huggingface.co/RabbitDaisuke/Wholebody-Compact-20261102-a6fde3) |
| 非公開チェックポイント・勾配・継続情報 | [RabbitDaisuke/Wholebody-Compact-20261102-a6fde3-checkpoints](https://huggingface.co/RabbitDaisuke/Wholebody-Compact-20261102-a6fde3-checkpoints) |

## 学習の構成

各フェーズで2つのActionsジョブを同時に動かします。両ワーカーは同じステップの共通重みを読み、異なるデータシャードから2D損失と3D損失の勾配を計算します。ワーカーごとにOptimizerを進めることはしません。rank 0が両者の寄与を集約し、共通のAdamWを1回更新して次の共通状態を保存します。

勾配は処理サンプル数に対応して集約します。2Dと3Dは別の教師データなので、それぞれの損失・有効ラベルを区別し、存在しないラベルに正解値を作りません。勾配のステップ、元のチェックポイント、ワーカーIDを対応付け、別ステップの勾配や同じ寄与の重複適用を防ぎます。学習ログには各ワーカーのステップ・シャード・計算時間・寄与を残します。

既定は128更新のフェーズを2段つなぐ構成です。後半の並列ジョブは、前半で保存したモデル・AdamW状態・進捗を読み、同じ学習を継続します。6時間制限は各Actionsジョブに対するものとして、保存と公開に時間を確保します。途中終了時も保存済みの共通状態を継続に使える構成です。

## データとモデル

| 項目 | 既定の構成 |
|---|---|
| 2D教師 | COCO-WholeBody v1.0。COCOの公式train/val分割を維持 |
| 画像取得 | COCO画像をS3配布元などから直接取得。既定は8,192画像を選び、その有効な人物クロップを学習 |
| 3D教師 | ASPset-510の関節、カメラ、分割情報。3D関節の投影から2D→3D学習用の組を生成 |
| 画像特徴 | Torchvision MobileNetV3 SmallのImageNet初期重みから、特徴ブロック0～8を使用。既定はbackboneを固定 |
| 2D推定 | 共有32チャンネル、入力に対してstride 8の位置推定ヘッドとセル内オフセット |
| 3D推定 | 幅128の2D→3D推定ヘッド。12身体関節を実測3D教師で学習 |
| 入力 | 人物1人のRGBクロップ、`float32 [N,3,192,144]`、値域0～1 |
| 2D出力 | `keypoints2d [N,73,2]`、クロップ内の正規化座標 |
| 2Dスコア | `confidence2d [N,73]`、位置推定の集中度。可視性の校正済み確率ではない |
| 3D出力 | `body3d [N,12,3]`、左右股関節の中点を原点とするカメラ座標、メートル |
| 複数映像 | 可変のバッチ次元`N`に独立した人物・カメラのクロップをまとめ、同じモデルを使用 |

現在の2D出力は、実際に存在する教師から選んだ身体12点・指40点・足6点・顔15点です。73という総数を恒久的な達成条件にするものではありません。関節の配列順、元データのID、座標軸、前処理、入出力名は公開する`schema.json`に記録します。

| 部位 | 使用する点と意味 |
|---|---|
| 身体12点 | 左右の肩・肘・手首・股関節・膝・足首。3D教師と対応する点もこの12点 |
| 指40点 | 片手5指×4点。手のルートは身体の手首と共有し、同じ手首を重複して出力しない |
| 足6点 | 左右の母趾先端・小趾先端・踵。足首は身体の点を共有 |
| 顔15点 | 口角と口の内側上下の4点、鼻先1点、左右それぞれ目頭・目尻・上下まぶたの計8点、左右の頬側の顔輪郭2点 |

顔の左右は本人から見た左右です。目頭・目尻から求める中心は眼領域の中心であり、瞳孔や視線の教師ではありません。頬側の2点は顔輪郭の教師で、頬表面や頬骨の正解位置ではありません。口の内側上下と上下まぶたを残して、口の開閉とまばたきに必要な位置情報を保持します。

手・掌の中心や2D上の向きは、手首と指の付け根などの骨格から導出します。手の甲の表面を独立に学習した出力や、実測された3D法線とは扱いません。足も踵と母趾・小趾から2D方向を求められますが、それだけで3Dの足裏法線が決まるわけではありません。

## 推論コストの設計

関節の選択に加え、MobileNetV3の後段ブロックを取り除き、共有ヘッドを32チャンネルに縮小し、stride 8のセルとセル内オフセットで位置を表現します。backboneの固定は学習時の計算を減らす設定であり、それ自体を推論の高速化とは数えません。

旧構成の133点×48×36と比較すると、現在の73点×24×18のヒートマップ本体は229,824要素から31,536要素になります。これは形状から計算した約86%の削減で、オフセット用テンソルやbackboneの計算は含みません。推論全体の速度やGPU使用率が同じ割合で改善したという測定結果ではありません。

複数カメラは1つの可変バッチにまとめて同じ重みを利用できます。バッチ内の推論は独立しており、複数視点を幾何的に統合する機能とは区別します。実際のGPU負荷は実行環境・バッチ数・並行する処理に依存し、現時点でGPU使用率の実測値は提示していません。

画像は人物のクロップを入力する前提です。人物検出器、カメラアプリ、VRChat・SteamVR・VRM連携は含みません。3Dは身体の相対姿勢であり、人物までの絶対距離やルート移動量を出力しません。顔・手指・足先について、3D正解ラベルがあるかのような出力は追加しません。小さく写った顔や指の精度は入力の解像度にも制限され、関節選択だけで実用精度に到達したとは判断しません。

## Actionsの設定と実行

リポジトリのActions secretに`HF_TOKEN`を設定します。トークンは`RabbitDaisuke`配下で指定リポジトリを作成し、ファイルを書き込める権限が必要です。トークン自体をソースコードやログに記載しません。Hugging Faceリポジトリの作成はActions内で行います。

リポジトリの **Actions** から `Train and publish WholeBody ONNX` を実行します。学習コードや設定などの対象ファイルを`main`へpushした場合も開始します。データ取得、共通状態の初期化、前半の並列学習、チェックポイントを引き継ぐ後半の並列学習、ONNX生成、公開を順に進めます。実際に読み込んだチェックポイントのステップと、その後の更新をログに記録します。

データセットの大容量アーカイブをActions Artifactへ繰り返し保存する構成にはしていません。永続化する学習状態・必要なログと、公開するモデルを分けます。通信失敗や途中終了から回収できるのは保存済みの状態です。失敗した処理まで学習完了として扱うことはありません。

## 公開する成果物

公開先には、学習済み`wholebody.onnx`、関節・座標系を含む`schema.json`、実行時の`metrics.json`、使用データの記録、モデルカード、ライセンスとクレジットを配置します。ONNXは共通チェックポイントの学習済み重みから生成し、実際の検証用クロップについてPyTorchとONNX Runtimeの出力差を記録します。

2D評価はCOCO検証画像を使用します。3D評価はASPset検証データの正解2D投影を入力した推定誤差です。この3D値を、RGBから全処理を通した3D精度と読み替えることはできません。学習ステップ数やファイルの公開だけで、実用精度への到達を保証するものでもありません。精度・実際の学習件数・実行資源・並列ワーカーの寄与は、その実行から生成された記録で確認できます。
